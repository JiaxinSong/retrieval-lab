# Retrieval Lab

Three-way hybrid retrieval over the PostgreSQL 17 docs — dense + lexical + identifier search, RRF fusion, Cohere reranking — with an LLM-judged evaluation pipeline and cited, agentic answer generation.

Built from scratch in plain Python (no LangChain) to measure what each retrieval stage actually contributes, and whether the answers built on it are faithful and correct.

## Corpus

1,293 section-aligned chunks (512 tokens, 64-token overlap) from 224 pages across 21 chapters of the PostgreSQL 17 docs. Questions are drawn from 5 chapters; the other 16 are distractors that compete for top-k slots but are never the source of a question. Every chunk carries its heading chain as a prefix, so it keeps its topic when read in isolation.

## Retrieval

- **Three retrievers**
  - **Dense**: `text-embedding-3-small` vectors in pgvector with an HNSW index (cosine)
  - **Lexical**: Postgres full-text search (`tsvector`) with OR semantics; high-document-frequency terms are filtered out as a stand-in for IDF, which `ts_rank` lacks
  - **Identifier**: exact matching on a `text[]` column for snake_case names like `work_mem`, which the full-text parser splits into `work` + `mem`
- **Reciprocal Rank Fusion** (k=60) merges the three ranked lists
- **Cohere cross-encoder reranking** (`rerank-v3.5`) over the top 40 fused candidates
- **Per-section cap** (at most 2 chunks per section), applied after reranking so it removes redundant chunks rather than relevant ones

## Answers

- **Cited answers**: the model answers only from retrieved passages, through a tool with a strict schema — answer text, the passage numbers it cites, and whether the passages answer the question at all. Citations map back to chunk URLs.
- **Agentic retry, gated by the rerank score**: if the top rerank score is below 0.5, the model gets a `search_docs` tool and may rewrite the query and search again, up to three searches. Otherwise it answers in one call.
- **Refusal instead of invention**: when the passages don't answer the question, the model says so (`answerable: false`) rather than filling the gap from its own knowledge.

## Evaluation

- **Question generation**: an LLM writes questions from sampled chunks, then a second pass rewrites each one as an engineer's search query without seeing the source passage. Questions that reuse a distinctive 5-gram from the source are dropped as leakage. Nothing else filters them: dropping questions the system ranks poorly would bias the test set toward the system being tested.
- **Hand-written questions** cover what generation can't: parallel and sequential multi-hop, same-section disambiguation, and near-domain unanswerable questions.
- **Pooled judging**: each question's pool is the union of all three retrievers' top 20 plus neighbouring chunks, so every configuration's top 5 is fully judged.
- **LLM judges**: two judges from different vendors (OpenAI and Anthropic) label every (question, chunk) pair. The weaker label wins, and yes/no conflicts go to a third referee model. Judges must pass calibration on hand-verified cases before the run, and inter-judge agreement is reported as Cohen's kappa.
- **Ground truth is a set**: a question is answered by *any* one of several chunks, or by *all* of a small combination that both judges agree is required. Ambiguous questions are discarded, not hand-fixed.

- **Answer judging**: the same two judges read every generated answer twice — against the passages it cites (faithfulness: is every claim supported?) and against the ground-truth chunks (correctness: correct, incomplete, or incorrect?). Instead of hand-labelled calibration cases, code plants known errors in copies of real answers (a changed value, an invented sentence, half of a multi-hop answer removed), and both judges must catch them before the run.

Metrics: Recall@5, MRR, distractor intrusion rate; answer faithfulness and correctness.
Configurations: vector, lexical, identifier, hybrid, hybrid without the section cap, hybrid + rerank, hybrid + cap-then-rerank, hybrid + rerank without the section cap, vector + rerank.

Ground-truth labels are generated by LLM judges, not human annotators. They are suitable for comparing retrieval configurations against each other, not as an absolute measure of quality.

## Results

84 LLM-judged questions (82 answerable, including 3 multi-hop questions that need two chunks), top 5. Every chunk returned by every configuration had been judged.

| Configuration | Recall@5 | MRR@5 | Hit@1 |
| --- | --- | --- | --- |
| vector | 0.915 | 0.807 | 0.720 |
| lexical | 0.768 | 0.648 | 0.561 |
| identifier | 0.433 | 0.359 | 0.305 |
| hybrid (RRF + section cap) | 0.872 | 0.751 | 0.646 |
| hybrid, no section cap | 0.884 | 0.753 | 0.646 |
| vector + rerank | 0.945 | 0.913 | 0.890 |
| **hybrid + rerank** | **0.976** | **0.929** | **0.902** |
| hybrid + cap-then-rerank | 0.939 | 0.895 | 0.866 |
| hybrid + rerank, no section cap | 0.963 | 0.925 | 0.902 |

- **Reranking is the stage that pays**: +9 questions over plain hybrid, none lost; Hit@1 0.646 → 0.902.
- **Fusion without reranking hurts**: RRF over three retrievers loses to vector search alone (−2 questions) on these paraphrased, natural-language questions; the section cap is not the cause.
- **Fusion with reranking helps**: hybrid + rerank beats vector + rerank by 3 questions and loses none, and is the only configuration that finds every required chunk of every multi-hop question — fusion contributes candidates, the reranker contributes order.
- **Rerank before the section cap** beats the original order by 3 questions; the cap itself trades no recall for diversity.

Differences under two questions are treated as noise. Full analysis and limits: `scripts/notes/07-evaluation.md`.

**Answers** (`scripts/notes/08-agent.md`):

- Every question whose retrieval found its ground truth got an answer citing it (80 of 80), and each multi-hop answer cited both required chunks. No invalid citations.
- No answerable question was refused; both near-domain unanswerable questions (Citus, pgpool-II) were.
- Forcing the agentic loop on every question: the model searched again on only 8 of 84, refused nothing it shouldn't, and recovered 1 question by rewriting the query with a setting name from its own knowledge — query expansion, not a multi-hop chain. The multi-hop questions never needed a second search, so the loop's main purpose remains untested.

**Answer quality** (`scripts/notes/09-answer-judge.md`), 82 answerable questions, two judges:

- **No answer is flagged as unfaithful by both judges**, and both judges catch every planted invented sentence. The single-judge flags are small additions from general knowledge (expanding "WAL"), not invented facts.
- **69 of 82 answers are correct by both judges.** Four are flagged by both; read against the chunks, three are real problems and one is a judge error.
- **Two of the three real problems are retrieval misses**: the only two answerable questions whose retrieval missed the ground truth produced confidently incomplete answers. The third is a reasoning error on a vague question.
- Inter-judge kappa is low (0.25 correctness, −0.05 faithfulness) because flags are rare and the judges flag different borderline answers; only flags both judges share are treated as findings.

One quirk the demos show: when the model refuses, it still cites every passage it read (nine in the Citus example), although none supports an answer. A refusal should carry no citations; the answer tool doesn't enforce that yet.

## Getting Started

### 1. Start PostgreSQL with pgvector

```bash
docker run -d --name pgvector \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=ragdb \
  -p 5432:5432 \
  pgvector/pgvector:pg17
```

The `vector` extension, tables, and indexes are created by the ingest script. To inspect the database:

```bash
docker exec -it pgvector psql -U postgres -d ragdb
```

### 2. Configure environment variables

```bash
cp .env.example .env
```

Fill in `.env`:

```
OPENAI_API_KEY=
COHERE_API_KEY=
ANTHROPIC_API_KEY=
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/ragdb
```

### 3. Install dependencies

Tested with Python 3.12. `requirements.txt` pins the direct dependencies to the versions the results were produced with.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 4. Load the database

The chunked corpus and evaluation files are committed, so the quickest path is to embed and load the existing chunks:

```bash
python scripts/03_ingest.py              # embed chunks.json and load into Postgres (~$0.01)
python scripts/04_hybrid_search.py       # demo: every retrieval stage for sample queries
python scripts/08_agent.py --ask "Is work_mem a per-connection limit?"   # a cited answer
```

This needs `OPENAI_API_KEY` for ingest and answers, and `COHERE_API_KEY` for reranking. Chunk ids are assigned in `chunks.json` order, so they match the ids in `eval/golden.json`.

### Rebuilding from scratch (optional)

```bash
python scripts/01_fetch_docs.py               # scrape the docs into data/raw/
python scripts/02_chunk_docs.py               # section-aligned chunks -> data/processed/chunks.json
python scripts/03_ingest.py                   # embed and load into Postgres
python scripts/05_generate_questions.py       # candidate questions -> eval/candidates.json
python scripts/06_build_golden.py --dry-run   # count judge calls, spend nothing
python scripts/06_build_golden.py             # LLM-judged golden set -> eval/golden.json
python scripts/07_evaluate.py                 # score nine configurations -> eval/results_summary.json
python scripts/08_agent.py                    # cited answers on the golden set -> eval/answers.json
python scripts/09_judge_answers.py            # judge the answers -> eval/answer_eval.json
```

Step 01 fetches the live documentation. If any page has changed since the committed snapshot, chunk contents and ids change too, and the committed evaluation files no longer apply: steps 05 and 06 must be re-run. Step 06 makes a few thousand judge calls (a few dollars) and caches every judgment in `eval/judgments.jsonl`, so an interrupted run resumes without paying twice.

Design notes for each step are in `scripts/notes/`; Chinese versions are in `scripts/notes/zh/`.
