# Retrieval Lab

Three-way hybrid retrieval over the PostgreSQL 17 docs — dense + lexical + identifier search, RRF fusion, Cohere reranking — with an LLM-judged evaluation pipeline.

Built from scratch in plain Python (no LangChain) to measure what each retrieval stage actually contributes.

## Corpus

1,293 section-aligned chunks (512 tokens, 64-token overlap) from 224 pages across 21 chapters of the PostgreSQL 17 docs. Questions are drawn from 5 chapters; the other 16 are distractors that compete for top-k slots but are never the source of a question. Every chunk carries its heading chain as a prefix, so it keeps its topic when read in isolation.

## Retrieval

- **Three retrievers**
  - **Dense**: `text-embedding-3-small` vectors in pgvector with an HNSW index (cosine)
  - **Lexical**: Postgres full-text search (`tsvector`) with OR semantics; high-document-frequency terms are filtered out as a stand-in for IDF, which `ts_rank` lacks
  - **Identifier**: exact matching on a `text[]` column for snake_case names like `work_mem`, which the full-text parser splits into `work` + `mem`
- **Reciprocal Rank Fusion** (k=60) merges the three ranked lists
- **Cohere cross-encoder reranking** (`rerank-v3.5`) over the top 40 fused candidates
- **Per-section cap** (at most 2 chunks per section), applied after reranking so it removes redundant chunks rather than relevant ones

## Evaluation

- **Question generation**: an LLM writes questions from sampled chunks, then a second pass rewrites each one as an engineer's search query without seeing the source passage. Questions that reuse a distinctive 5-gram from the source are dropped as leakage. Nothing else filters them: dropping questions the system ranks poorly would bias the test set toward the system being tested.
- **Hand-written questions** cover what generation can't: parallel and sequential multi-hop, same-section disambiguation, and near-domain unanswerable questions.
- **Pooled judging**: each question's pool is the union of all three retrievers' top 20 plus neighbouring chunks, so every configuration's top 5 is fully judged.
- **LLM judges**: two judges from different vendors (OpenAI and Anthropic) label every (question, chunk) pair. The weaker label wins, and yes/no conflicts go to a third referee model. Judges must pass calibration on hand-verified cases before the run, and inter-judge agreement is reported as Cohen's kappa.
- **Ground truth is a set**: a question is answered by *any* one of several chunks, or by *all* of a small combination that both judges agree is required. Ambiguous questions are discarded, not hand-fixed.

Metrics: Recall@5, MRR, distractor intrusion rate.
Configurations: vector, lexical, identifier, hybrid, hybrid + rerank, hybrid + cap-then-rerank.

Ground-truth labels are generated by LLM judges, not human annotators. They are suitable for comparing retrieval configurations against each other, not as an absolute measure of quality.

## Getting Started

### 1. Start PostgreSQL with pgvector

```bash
docker run -d --name pgvector \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=ragdb \
  -p 5432:5432 \
  pgvector/pgvector:pg17
```

The `vector` extension, tables, and indexes are created by the ingest script. To inspect the database:

```bash
docker exec -it pgvector psql -U postgres -d ragdb
```

### 2. Configure environment variables

```bash
cp .env.example .env
```

Fill in `.env`:

```
OPENAI_API_KEY=
COHERE_API_KEY=
ANTHROPIC_API_KEY=
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/ragdb
```

### 3. Install dependencies

Requires Python 3.10 or later.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 4. Load the database

The chunked corpus and evaluation files are committed, so the quickest path is to embed and load the existing chunks:

```bash
python scripts/03_ingest.py              # embed chunks.json and load into Postgres (~$0.01)
python scripts/04_hybrid_search.py       # demo: every retrieval stage for sample queries
```

This needs only `OPENAI_API_KEY` for ingest and `COHERE_API_KEY` for reranking. Chunk ids are assigned in `chunks.json` order, so they match the ids in `eval/golden.json`.

### Rebuilding from scratch (optional)

```bash
python scripts/01_fetch_docs.py               # scrape the docs into data/raw/
python scripts/02_chunk_docs.py               # section-aligned chunks -> data/processed/chunks.json
python scripts/03_ingest.py                   # embed and load into Postgres
python scripts/05_generate_questions.py       # candidate questions -> eval/candidates.json
python scripts/06_build_golden.py --dry-run   # count judge calls, spend nothing
python scripts/06_build_golden.py             # LLM-judged golden set -> eval/golden.json
```

Step 01 fetches the live documentation. If any page has changed since the committed snapshot, chunk contents and ids change too, and the committed evaluation files no longer apply: steps 05 and 06 must be re-run. Step 06 makes a few thousand judge calls (a few dollars) and caches every judgment in `eval/judgments.jsonl`, so an interrupted run resumes without paying twice.

Design notes for each step are in `scripts/notes/`.
